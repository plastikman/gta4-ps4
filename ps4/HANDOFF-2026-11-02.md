# GTA IV PS4 handoff — 2026-11-02

## >>> LATEST (LX): the streamed record buffers all hold the SAME foreign bytes - read first <<<

LX's `[PS4 bad-count]` probe read each bad record through the game's `vC` view and straight
from the physical heap. Eight hits, six distinct 16 KiB-aligned buffers
(`cadb4000 cadb8000 cadc0000 cadc8000 cadd0000 cadd8000`, record indices 0x67-0x70), all:

    vC:   2ccd727b e3a0f205 4505a86b 945f2ec7 1000e900 c4ee4ca8
    phys: 2ccd727b e3a0f205 4505a86b 945f2ec7 1000e900 c4ee4ca8   (identical)

Ruled out by measurement:
- alias incoherence (vC == physical for every record)
- "never filled" (not 0xCD fill)
- raw archive bytes - the 24 bytes (and even the first 8) are in neither the base-game ISO
  nor Title Update 8, so they are produced at runtime on the console
- PS4-specific decompression - `gta4_lzx_hooks.cpp` (libmspack, host-side) has no platform code

Leading hypothesis, NOT yet measured: six different resources decoding to identical bytes is
what you get if **every streaming read returns the same data regardless of requested offset**
(identical compressed input -> identical decompressed garbage). The old "68-byte header read
returned 68 bytes" check verified length only, never offset.

**Next:** log each file read during streaming - handle, requested offset, length, first 16 bytes
returned. Different offsets returning the same bytes = PS4 file-I/O bug (e.g. offset lost in a
64-bit/endian conversion), fixed in the I/O layer, not the allocator/free/memory paths.

Precommit (`ps4_physical_precommit`, default on) is not a fix; keep or drop. LVI-LX probes are all
hard-filtered and cost nothing on healthy paths.

## >>> PREVIOUS (LIX): the -1 is an overflow guard on a garbage count <<<

LIX's `[PS4 bad-alloc]` probe (lr read at `sub_821B3510` entry, so it is the real call site)
caught the `0xFFFFFFFF` request on the first run - at least five times, all from
`lr=82514850` in **`sub_825147B8`**:

    r11 = [r20 + 4]                 // count, read from a streamed record (r20 = arg r4)
    r3  = r11 * 4
    [r30 + 88] = r11
    if (r11 > 0x3FFFFFFF) r3 = -1   // compiler overflow guard for `new T*[count]`
    allocate(r3)

So `-1` is not miscomputed: the **count read from the record is > 0x3FFFFFFF**. The fatal
15th `sub_82514AE0` call skipped loop2 (count read as <= 0 signed), which fits a count like
`0xCDCDCDCD` (uninitialised fill) rather than a byte-swapped small count.

Provenance: `sub_825147B8`'s only direct caller is `sub_82515B58` (an AABB-filtered walk),
which passes its own arg r4 through; valid back-chain frames are `sub_82679140+0x1d4` and
`sub_826799E0+0x48` (the streaming code under `sub_821D00D0`). The logged record pointers
`cadb4000 cadb8000 cadc0000 cadc8000 cadd0000` are all 16 KiB-aligned in `vC0000000`
(a physical alias) with r5 sizes 0x38a4-0x6d7c - streamed resource buffers.

Two explanations, different fixes:
- **A** - the buffer was never filled (a PS4 read/stream failure leaves fill bytes).

**Every hung run is in an infinite fault-recovery loop on one unbacked physical page.**
Found in the rex log, `/data/Liberty Recompiled/logs/Liberty Recompiled_NNN*.log` (NOT the
guest trace, NOT klog). Runs 430, 431 and 432 each contain ~31,000 copies per 5 MB rotation,

              (host 00000010A77B4000, guest_protect 0000000B)

- Same guest address, host page and protection in all three runs - deterministic.
- `0xA77B51C5` is in `heaps_.vA0000000`, a physical-heap alias. `0x0B` = Read|Write|WriteCombine
  (GPU-visible memory). Guest metadata says the page is committed and writable.
- Runs that had not reached the hang (433, 434) contain zero.

Mechanism (`src/system/xmemory.cpp`, `Memory::AccessViolationCallback`, physical-heap write
branch): guest metadata says writable -> `rex::memory::Protect(host page, kReadWrite)` ->
`return true` -> the store retries -> faults again -> forever. The recovery only restores
*protection*; it never ensures the page is *backed*.

Why PS4 only: `Memory::Initialize` on every other platform, **PS5 included**, pre-commits the
whole 512 MiB physical range read-write at startup "so the GPU can access it without page
faults". The PS4 port deliberately skips that (`#if REX_PLATFORM_PS4` "skipping eager 512 MiB
physical-memory precommit") and backs pages only "when the corresponding heap pages commit".
On PS5 this store would simply land on pre-committed memory.

The earlier PS4 symptom patch at hard-coded `0x10ac1244` ("commit and zero only the containing
Orbis page once, then resume") is the same class of failure fixed by address, not by cause.

**Proven:** the loop, its address, its determinism, the PS4-vs-PS5 precommit divergence, and
that the recovery path never backs the page.
**Not yet proven:** that this loop is what freezes the world-loader thread (as opposed to a
co-occurring loop on another thread), and which guest instruction issues the store. Note that
`d9ad83e0` (the block freed on the 15th `sub_82847618` release) is in `vC0000000`, not `vA`, so
the two have not been connected by evidence. Resolve that with a marker before claiming it.

**Next:** one package that (a) logs `rip` + thread once per new faulting address in the recovery
path, and (b) on PS4, when guest metadata says committed but the host page is unusable, actually
commit/back it instead of only re-protecting. If world loading then passes the 15th release,
cause and fix are confirmed together. Restoring the full 512 MiB precommit is the blunt
alternative/experiment; it was removed to save PS4 direct memory, so watch for OOM.

## THE CORRUPT NODE, DUMPED (LIV run)

## THE BAD STORE (still unexplained, probably the cause of the above)

`sub_82848B68` is the guest allocator's free; at `generated/gta4_recomp.65.cpp:75745`
it performs a doubly-linked free-list unlink:

    r9  = [r11+16]            // prev
    r10 = [r11+20]            // next
    if (next) [next+16] = prev     <-- faults

The captured fault, **identical in two independent runs**:

    op=write32 address=00001010 lr=82848c28
    r11 = d9ad83e0   (node)
    [r11+16] = d9ad83f0   prev  (== node + 0x10, not a plausible link)
    [r11+20] = 00001000   next  (invalid; passes the `next == 0` guard)

`next + 16` = `0x1010`, an unmapped low guest address. The store traps, rex's
access-violation path does not claim it, the handler returns, and the guest
**re-executes the same store forever**. That is the "hang": no crash, process
alive, world-step events frozen at a fixed count while other tracing trickles on,
CPU busy, sampled stacks varying between dumps.

Reached via: `sub_82514AE0` cleanup -> `sub_821B3560` thunk -> `sub_82847618`
(find owning allocator) -> `vtable[12]` -> `sub_828494D8` -> `sub_82848B68`.

**Still unknown: who writes `0x1000` into `[node+20]`.** Do not patch the unlink
to skip an implausible `next` - that masks heap corruption (see AGENTS.md).

### Why it loops (confirmed in the L run, 4 dump rounds)

`Memory::AccessViolationCallback` **claims** this fault. It finds a heap for guest
`0x1010`, decides the page should be writable, re-protects it and returns `true`;
the store faults again immediately. The allocator thread's `rip` cycles across
dump rounds between `sub_82848B68`, `BaseHeap::QueryProtect`/`QueryRegionInfo`
and kernel code - a fault/handle/retry cycle, not a spin and not a deadlock.
`sub_82848B68` contains **no backward branch at all**, so it cannot loop itself.

Because the fault is claimed, execution never reaches the "nothing took it"
branch, so L's `UnhandledHostFault` change could not fire. Two readings I had
wrong before this: it is not a `RtlEnterCriticalSection` deadlock (the wait slots
are empty and only `RtlLeave` appears in the stacks), and it is not a loop inside
`sub_82848B68`.

## Instrumentation lessons

- **Do not poll the console's FTP aggressively (standing instruction).** On 2026-11-02 the
  accumulated pollers (~16 klog receivers, one left running per package, plus 15 s FTP
  followers/waiters) killed GoldHEN's FTP (2121) and klog (3232) servers mid-run and the
  console had to be rebooted. Use one klog receiver and one trace follower per run, poll
  FTP no faster than about every 60 s, and stop both before arming the next run. The old
  `watch-coredump.py` pollers on the build host belong to other work; leave them alone.

- `AGENTS.md` forbids capping events; sampling is fine. Honour both.
- **Check a function's call frequency before instrumenting it.** Marking `sub_821B3560`
  unconditionally made it 97% of the trace (1,700+ events per unit of real startup work) and
  starved the boot — it never reached the carousel. Fixed by filtering on the one caller:
  `ctx.lr == 0x82514C4C` (the thunk tail-dispatches with `bctr`, so `lr` still holds the
  caller's return address). Volume went to zero outside that site.
- The trace file is append-only and shared across runs. Record its FTP `Content-Length`
  **before** each launch and slice from that byte; also record where a given package's own
  output starts when a previous run's tail got captured.
- Marker names unique to a package (e.g. `finalize2-*`, `thunk-*`) make runs unambiguous
  even when offsets get muddled. Keep doing that.
- Do not extrapolate a completion ETA from one short rate sample. A 5-records/60s window on
  XLIII projected ~77 minutes; it had in fact stalled minutes later.
- `pgrep`/`pkill -f` on a pattern that also appears in the running command kills your own
  shell (exit 144). Match on a pattern that excludes it, or kill by PID.
- **`create-fself` can fail while the build reports success (exit 0).** It printed
  `Failed to build FSELF: missing library for symbol (__wrap_malloc)` and left a
  stale `eboot.bin` with its old mtime and hash. Always verify the EBOOT's hash
  changed versus the previous package before staging.
- The generated code shadows non-volatile registers with **locals**
  (`PPCRegister r29{}, r30{}, r31{}`), while the crash tracer prints `ctx.rN`.
  Only the `ctx` registers a function actually uses are meaningful in a dump;
  `r31=0` there means nothing.

## LATEST (LXIV: root cause of the streaming-handle scramble)

LXIII (memory backend rework) confirmed the commit-over-live bug was real (>1000 commits over
live pages in minutes) and boots fine, but the update.img off=0 reads still came back.
Its pattern was decisive: in each streaming batch the 1st request is correct, the 2nd has a
neighbour's offset, and the rest have handle 0 (update.img @0).

Root cause: a leftover PS4 debug line in generated/gta4_recomp.66.cpp, sub_8284CB80:
`r28.u64 = ctx.r11.u64;` before the vtable[72] bctrl at 0x8284CC8C. r28 is the base of a
free-list slot table (0x82192FAC, 28-byte entries, head index at [r28-24]). The function
pops the head at the end with `stw r11,-24(r28)`. With r28 overwritten by the call target,
that store hit code (0x8285E930 / 0x82513030 = target-24), the PS4 write guard dropped it,
and the free-list head never advanced: every open reused the same slot. The same line was
also in sub_8285DE00 (before bctrl 0x8285DEA4). Neither line exists in the PS5 release.
LXIV removes both (eboot c05c3045feccaf0e…, pkg 1a30dc709720bcd3…), on top of LXIII.
Expected: no `[PS4 guest write site]` lines for 8285e930/82513030, no update.img off=0
WINDOW reads, no bad-count, and the world load completes.
Lesson: audit generated-code diffs for unsaved assignments to guest locals
(`git diff -U0 generated | grep '^+' | grep -E 'r[0-9]+\.u64 ='`).

## LATEST (PS4 vs PS5 diff → LXIII memory backend rework)

The systematic diff found that the PS4 tree carries about a dozen hand patches in the
recompiled guest code (skipped calls, forced returns, low-pointer guards). Most cover objects
that were "not created yet / uninitialized / null" (sub_825147B8 0x81818181 skip,
sub_825FC660 null global, sub_828BF280 device object, sub_82A3BF50/C2B8 D3D resources,
sub_82848B68 junk pointers, strtol(0x8)). None of them were needed on PS5. Root-cause
candidate, confirmed statically:
src/core/memory_ps4.cpp AllocFixed mapped *fresh* direct memory MAP_FIXED on every commit,
rounded to 16 KiB, even over ranges that already had backing. BaseHeap::AllocFixed explicitly
allows re-committing committed pages, and v00000000 uses 4 KiB guest pages, so a commit
discarded live data: the re-committed pages themselves and up to 3 neighbouring guest pages per
16 KiB host page. PS5 (MapViewsPs5) and POSIX map guest memory once, so commit = protect only.

LXIII (eboot 41bc1932d28f…, pkg a2b3f84d6cba…): memory_ps4.cpp keeps a per-16 KiB page table
of direct-memory backing over [0x1000000000, +8 GiB). Commits back only unbacked pages
(zero-filled) and just mprotect live ones. Physical aliases take their dmem offset from that
table and skip identical remaps. `[PS4 commit-over-live]` logs commits that hit live pages
(each one would have wiped data before). The 0x10ac1244 fault hack no longer memsets 16 KiB.
The guest-code band-aids are still in place; remove them once LXIII is confirmed.

## LATEST (LXI result → LXII fix candidate)

LXI ([PS4 read] probe in XFile::ReadInternalLocked) showed the bad streamed records are
`update.img` read at **offset 0** (its AES-encrypted IMG header, bytes 2ccd727b…), with lengths
that exactly equal nj_01.img `.xpl` entries [31]–[42] (strbig0–2, stream0, stream1, stream10–16).
The two "good-looking" nj_01 reads were also wrong: off 0x108d800 (stream10) + len 0x3994 (strbig1),
off 0x10b9800 (stream19) + len 0x43a4 (stream14). So streaming handles (image+offset) are scrambled
or zeroed (handle 0 → image 0 = update.img, offset 0) while the sizes stay correct.
update.img on the console is byte-identical to the local copy and decrypts fine (19 .sco entries,
none at offset 0). The file and I/O layers are not the problem.

Root-cause candidate: `rexcrt_memcpy` → `std::memcpy`. The PS4 eboot statically links
OpenOrbis/musl memcpy (gta4.oelf @0x7cce110), a strict forward copy with no overlap handling.
The 360 MSVC CRT memcpy and the FreeBSD/PS5 libc memcpy are overlap-safe. Guest code that shifts
arrays up with memcpy therefore corrupts tables on PS4 only.

LXII (eboot 042761065be3…, pkg 7f30b0c2d127…): src/kernel/crt/memory.cpp routes memcpy, XMemCpy
and memcpy_s through memmove (all platforms), and on PS4 logs `[PS4 memcpy-overlap]` to the guest
trace (first hit per guest lr, plus every 1000th; UP = dst>src = would smear on musl).
Expected: overlap UP lines appear, the update.img off=0 reads disappear, and the world load proceeds.

**LXII RESULT: memcpy theory DISPROVED.** Zero `[PS4 memcpy-overlap]` lines over the whole run,
and the identical update.img off=0 reads (same lengths, same cadb4000… buffers) plus bad-count
recurred. The memmove routing is harmless and was left in. The handle scrambling for the
nj_01 `.xpl` entries [31]–[42] has some other cause. Next: find statically where the
streaming slot handle (image index + block offset) for streamed IPLs (.xpl) is written,
and compare it with where the size is written.
